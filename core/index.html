01

Why I built it

My first assistants ran as n8n workflows. They worked, but the logic was spread across nodes and Google Sheets, and almost every day I had to open a workflow and fix something. I couldn't test a change before it reached a real customer.

So I moved the logic into one Python service that I can test, review and deploy like normal software. Each channel is a thin adapter; the conversation logic is shared. The n8n workflow I replaced is still there, switched off, as a rollback path.

03

What happens to one message

  1. The adapter checks the channel's signature and size limit, then turns the payload into one common IncomingMessage.
  2. Rate limit per conversation, plus a global hourly cap per demo profile.
  3. The message is saved with its channel ID, which is unique in the database. If WhatsApp retries the same webhook, the second copy is ignored.
  4. The last messages of this conversation go to Claude with a layered prompt: shared rules plus a file for the channel. The static part is cached.
  5. If Claude decides a person should follow up, it calls a tool. The lead waits in the database, picks up new details, and goes to Telegram as one complete message 5 minutes after the last update.
  6. An empty reply is retried once; if Claude still fails, the visitor gets a short fallback, and the error is reported to me.
  7. The reply is saved and sent back the channel's own way.
# memory.py (comments translated) — a webhook retry must not produce a second answer
async def save_user_message(session, conversation_id, text, message_id, rate_limited=False) -> bool:
    """Save an incoming message. False if this message_id was already seen."""
    session.add(Message(conversation_id=conversation_id, role="user", content=text,
                        message_id=message_id, rate_limited=rate_limited))
    try:
        await session.commit()
    except IntegrityError:      # unique constraint on message_id
        await session.rollback()
        return False
    return True
04

How I keep it from breaking

  • Tests. 170+ pytest tests in 14 files: webhooks and signatures, memory, rate limits, lead buffering and dedup, prompts, each demo profile, security limits. The external APIs (Claude, Meta, Telegram) are always mocked, so tests cost nothing.
  • CI on every push. ruff lint and format, the full test suite against a real PostgreSQL 16, then a Docker build of the same image the server runs, with a smoke check inside it.
  • Pull requests only. Nothing goes to main directly. I merge every PR that touches production myself; PRs that change only tests or docs merge on their own. PRs that touch deploy files, dependencies or bot logic come to me flagged for a closer look.
  • Pull-based deploy. The server checks main every 2 minutes. Before switching it backs up the database, then waits until /health reports the new commit and /ready can reach the database.
  • Automatic rollback. If the new version fails the check, the server goes back to the previous commit and tells me in Telegram. After a schema migration it does not roll back on purpose, because old code can't run on the new schema. That's why migrations here only ever add things.
  • Alerts and backups. Errors reach my Telegram, no more than once every 10 minutes per error. All databases are backed up daily and kept for 14 days.

05

AI-specific safety

  • Prompt-injection runs. A QA script attacks the live prompt with a hidden canary code planted in it. The run fails if the canary or any piece of the system prompt shows up in a reply.
  • Stays in its lane. Each assistant answers only from its own knowledge, doesn't invent prices or specs, and the demo bots refuse off-topic requests politely.
  • Untrusted input stays data. Visitor names and page languages are cleaned or whitelisted before they reach the prompt.
  • Costs and keys. Every profile has its own API key with a spending limit, plus per-conversation and per-profile hourly limits. Secrets never appear in code, tests or logs.

Load test: the bottleneck I found

I ran the core on a local copy with PostgreSQL and replaced Claude with a stub that answers in 2 seconds, like a real model reply. Then I sent hundreds of website chat messages from 10 to 80 visitors at once.

Up to 10 visitors it was fine. Above that, throughput stopped at about 5 requests per second and waiting time grew to 14 seconds. The reason: each request kept its database connection while waiting for Claude, and the pool has 10 connections. Releasing the connection before the Claude call fixed it on the test copy:

Before and after: NorthFrame requests

In n8n, a workflow read a Google Sheet every minute to find new requests: once a minute, around the clock: about 1,440 runs a day, 1.4 s each, even when nobody wrote in. It was switched off when NorthFrame moved to the core. In the core, a background task checks its own PostgreSQL table every 30 seconds, and a request that wasn't sent yet survives a restart. The one real request so far reached the coordinator's Telegram 14 seconds after it was submitted, including the AI triage.

07

How I work on it

I don't type most of this code by hand. I decide what to build and how it should be structured, Claude Code writes the change, and I read the diff, run it and merge it. The tests and CI exist so that neither of us has to take the other's word for it. When production misbehaves, I start from the logs.

The repository is private because it serves a live business number. I'm happy to walk through it on a call or give read access to a reviewer.
